# terre-lab: 11/6 구성을 재현해서 재는 실험실

같은 공용 교육 서버 안에 운영(terre-service)과 완전히 분리된 실험실(terre-lab)을 띄워서,
11/6 구성의 문제를 직접 재고(개선 전), 나중에 개선한 구성을 같은 조건으로 다시 잰다(개선 후).

## 실행 순서 (로컬 PC에서 더블클릭)

| 파일 | 하는 일 | 걸리는 시간 |
|---|---|---|
| `1-lab-up.cmd` | 실험실 파일을 서버로 올리고 실험실을 띄운다. 이때 최신 운영 백업을 실험실 DB로 복원하므로 **T4(복원 시간)가 함께 측정**된다 | 5~15분 |
| `2-lab-test.cmd` | 번호를 골라 시험 1개를 돌린다: 1 T1 지도 타일 부하, 2 T2 사업장 분석 부하, 3 T3 배포 중 끊김, 4 T4 복원 다시, 5 T5 backend 장애, 6 T5 DB 장애 | 6~25분 |
| `3-lab-status.cmd` | 실험실·운영 상태를 보고 결과를 PC로 가져온다 | 1분 |
| `9-lab-down.cmd` | 실험실을 지운다(YES 입력). 마지막 정리 때는 PURGE까지 입력 | 1분 |

- 결과는 `infra-portfolio\lab-results\날짜-시각-시험이름\` 에 모인다. `result.md` 가 사람이 읽는 표다.
- 창을 닫아도 서버에서는 시험이 계속된다. 나중에 `3-lab-status.cmd` 로 결과를 가져오면 된다.
- 시험은 한 번에 하나만 돈다.

## 운영을 지키는 장치

- **분리:** 프로젝트 이름 terre-lab. 컨테이너·네트워크·저장 공간이 운영과 섞이지 않는다. 포트는 서버 안(127.0.0.1:18088)에만 연다.
- **자원 상한:** 실험실 전체를 `terrelab.slice` 에 넣고 CPU 2개·메모리 4GB 상한, CPU가 모자랄 때 운영보다 낮은 우선순위(CPUWeight 20)를 건다. 부하 도구는 CPU 0.5개. 상한이 확인되지 않으면 실험실을 지우고 멈춘다.
- **시작 조건:** 팀 CI 작업이 돌고 있거나, 새벽 4시 백업 시간대(03:50~04:20)거나, 운영 응답이 1초를 넘거나, 서버 여유(메모리 6GB·디스크 20GB)가 부족하면 시작하지 않는다.
- **감시:** 시험 중 10초마다 운영 응답을 확인하고, 1초 초과나 오류가 2번 연속이면 부하 도구와 실험실을 바로 멈춘다. 모든 결과에 '운영 영향' 기록(가장 느린 운영 응답)이 남는다.
- **이미지:** 서버에서 빌드하지 않는다. 지금 운영 이미지에 `terre-lab-backend:snap` 같은 이름만 하나 더 붙인다. 이름에 `/backend:` 같은 글자가 없어서 팀 CI의 이미지 정리 규칙(최근 5개만 남김)에 영향을 주지 않는다.
- **비밀값:** 운영 `.env` 는 읽지 않는다. 실험실 비밀값은 서버에서 새로 만들고(권한 600) 화면에 출력하지 않는다.
- **데이터:** 최신 운영 백업을 읽어서 실험실 DB에만 복원한다. 복원 오류는 종류별 건수만 남기고, 값이 섞일 수 있는 줄은 버린다. 테스트 계정은 `lablt-NN@example.com` 으로 실험실 DB에만 만든다.
- **정리:** `9-lab-down.cmd` 가 컨테이너·저장 공간·네트워크를 지우고 자원 상한 설정을 되돌린다. PURGE면 실험실 이미지 이름과 서버 폴더까지 지운다. 서버 회수(11/27) 전, 11/26까지 끝낸다.

## 11/6과 같은 점, 다른 점

- 같음: 서비스 5개, 메모리 상한, 로그 상한, 자동 재시작, backend 준비 상태 검사, web 의 nginx 설정(`nginx-1106.conf` = 4ae439fb 의 frontend/nginx.conf), 첨부를 서버 디스크에 저장
- 다름(실험실이라서): 전체 CPU 2개·메모리 4GB 상한, 포트를 서버 안에만, DB·Redis 포트는 열지 않음, 앱 이미지는 지금 운영 이미지, screening 은 외부 AI 없이 규칙 모드, 비밀값은 실험실 전용

## 시험 내용

| 시험 | 하는 일 | 주요 지표 |
|---|---|---|
| T1 지도 타일 | 팀 11/5 시나리오 A(로그인 없이 지도 열기). 동시 10·25·50·75·100명 단계마다 2분 유지 | p95·에러율·초당 요청, 목표를 지킨 최대 동시 사용자, DB CPU |
| T2 사업장 분석 | 팀 11/5 시나리오 B(로그인 후 사업장 분석). 같은 단계 | 위와 같음 + DB 활성 연결 수 |
| T3 배포 중 끊김 | 1초에 10번 요청하면서, 팀 CI처럼 backend·screening·web 을 그 자리에서 새로 만든다 | 실패 요청 수, 끊긴 시간 |
| T4 백업 복원 | 최신 백업으로 DB를 복원하고 앱이 응답할 때까지 | RTO, RPO |
| T5 장애 회복 | 1초에 10번 요청하면서 backend 또는 DB 프로세스를 강제 종료(kill -9) | 실패 요청 수, 정상화까지 시간 |

에러율이 10%를 넘으면 더 높은 단계는 하지 않는다(팀 시나리오의 자동 중단 기준과 같다).
