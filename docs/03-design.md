# 4. 비교와 개선 설계

설계 원칙은 하나다. **계산은 서버에 두고, 반복되는 것(타일)·보관할 것(백업)·바깥 입구는 서버에서 떼어 낸다.** 서버 한 대가 모든 일을 다 하던 구조에서, 서버가 하지 않아도 되는 일을 덜어 내는 방향이다. 각 문제마다 선택지를 비교하고 하나를 골랐다.

## 4.1 타일·분석: 계산 자체를 없앤다 (문제 1)

| 선택지 | 장점 | 한계 | 판단 |
| --- | --- | --- | --- |
| 요청마다 계산(지금) | 항상 최신 | 같은 계산을 사람 수만큼 반복 | 문제의 원인 |
| 서버 캐시(첫 요청 뒤 저장) | 설정만으로 가능 | 첫 요청은 여전히 느림. 공개 여부가 바뀐 보호지역이 옛 주소에서 계속 보일 수 있음 | 보호지역에는 맞지 않음 |
| **미리 생성(선택)** | 계산을 요청 전에 끝냄. 파일로 바로 응답 | 변경을 반영할 장치가 필요. 범위를 정해야 함 | **반복 계산을 0으로** |
| DB 증설·분리 | 위치마다 다른 분석 계산까지 빨라짐 | 같은 계산의 반복은 그대로. 매달 비용이 계속 듦 | 남은 병목의 다음 단계 |

- **왜 미리 생성인가:** 첫 생성에 103초밖에 걸리지 않았다. 타일 하나는 혼자 만들면 빠르다는 뜻이다. 느림의 원인은 무거운 타일이 아니라 여러 사람이 같은 계산을 동시에 반복한 것이었고, 미리 만들면 그 반복이 사라진다.
- **범위:** 줌 5~12, 한반도 주변. 줌을 하나 올릴 때마다 타일 수가 약 4배가 되므로, 사람들이 가장 많이 보는 범위만 만들고 나머지는 지금처럼 backend가 만든다(파일이 없으면 backend로 넘김).
- **데이터 성격에 따라 두는 곳을 나눴다.**

| 데이터 | 성격 | 두는 곳 | 이유 |
| --- | --- | --- | --- |
| 행정구역(시군구·읍면동) | 거의 바뀌지 않음 | **S3 + CloudFront** | 서버와 분리해 배포·장애 중에도 응답, 사용자가 몰리면 엣지가 받음 |
| 보호지역 | 공개 여부가 수시로 바뀌고 즉시 숨겨야 함 | 서버 nginx 파일 + 변경 감지 | 5초마다 변경을 감지해 파일을 내리고(그동안은 DB가 정확히 그림) 다시 만들어 바꿔 끼움 |
| 범위 밖(줌 13 이상 등) | 요청이 드묾 | backend | 미리 만들 가치가 낮음 |

- **옮기며 생긴 빈틈과 보완:** 행정구역을 S3로 옮기자 미리 만든 범위 밖의 타일이 403으로 돌아왔다. 서버 nginx는 없으면 backend로 넘겼지만 S3에는 그 대체 경로가 없었기 때문이다. CloudFront의 origin failover(S3에 없으면 서버로)로 보완하는 설계를 넣었다.
- **DB 증설·분리는 다음 단계:** 사업장 분석은 위치마다 계산이 달라 미리 만들 수 없다. 이 병목은 쿼리 개선과 DB 분리·증설로 풀어야 하며, 계산을 줄이는 쪽을 먼저 한 뒤의 순서로 둔다.

## 4.2 배포: 새 버전을 먼저 띄우고 바꾼다 (문제 2)

| 선택지 | 판단 |
| --- | --- |
| 그 자리에서 다시 만들기(지금) | backend가 준비되는 약 40초 동안 받을 곳이 없음 |
| backend 여러 개 + 차례로 교체 | 부하 분산 장치와 상시 자원이 더 필요 |
| **블루-그린(선택)** | 쉬는 색에 새 버전을 띄워 준비를 확인한 뒤 입구만 바꿈. 실패하면 바꾸지 않음 |

- **구조:** 입구 nginx를 앱 nginx에서 떼어 내 항상 떠 있게 했다. 색깔별로 web·backend를 따로 두고, 입구는 설정 파일 하나(지금 색)만 바꿔 다시 읽는다(reload는 처리 중인 요청을 끊지 않음).
- **준비 확인:** backend 준비 상태(readiness)와 새 색 nginx를 거친 API 200을 모두 확인해야 전환한다. 확인에 실패하면 전환하지 않아 옛 색이 계속 서비스한다(자동 롤백).
- **한 서버의 함정:** 처음 시험에서 새 backend가 준비되는 동안 서비스 중인 색과 CPU를 다퉈 응답이 느려졌다. 준비하는 동안만 새 backend의 CPU를 0.7개로 묶고 우선순위를 낮춘 뒤, 전환 직후 풀도록 보완했다.
- **자동화(GitHub Actions):** main에 올리면 설정 검사 → 이미지 3개 빌드·GHCR 저장(커밋 해시 태그) → 배포 순서로 돈다. 서버에는 '배포 요청 한 줄'만 보낼 수 있는 제한 SSH 키로 들어가며, 키가 새어도 셸 접속·파일 복사는 할 수 없다. 이미지를 받는 데 쓰는 토큰은 워크플로가 끝나면 만료되는 임시 토큰이라 서버에 남지 않는다.
- **빌드 분리:** 이미지를 운영 서버가 아니라 GitHub 실행기에서 만든다. 빌드가 서비스 CPU를 쓰던 문제(관찰)도 이 구조로 함께 덜어진다.

## 4.3 백업: 서버와 운명을 떼어 낸다 (문제 3)

| 선택지 | 판단 |
| --- | --- |
| 같은 디스크(지금) | 디스크·서버 사고 때 원본과 함께 사라짐 |
| 다른 서버 | 그 서버도 관리해야 함 |
| **S3(선택)** | 서버와 무관하게 보관. 암호화·버전 관리·보관 기간을 설정으로 해결 |

- **권한:** 공용 서버에 AWS 키를 두지 않았다. GitHub Actions가 OIDC로 AWS 역할을 1시간만 받아 '파일 하나만 올릴 수 있는' 서명 주소를 만들고, 제한 키로 서버에 넘긴다. 역할은 올리기만 할 수 있어서, 서버나 CI가 털려도 기존 백업을 읽거나 지울 수 없다.
- **버킷:** 퍼블릭 차단, 기본 암호화, 버전 관리(덮어써도 이전 본이 남음), HTTPS가 아닌 접근 거부, 7일 뒤 자동 삭제.
- **백업 범위:** 개인정보와 고객이 만든 데이터 표는 구조만 넣고, 공공·참조 데이터는 그대로 넣었다. 덤프 내용은 열어 보지 않고 크기와 해시만 기록한다.
- **주기:** 매일 1번이다. RPO 1시간을 맞추려면 DB 변경 기록(WAL)을 계속 S3로 보내는 방식이 필요하며, 이것은 설계로 남긴다.

## 4.4 입구: HTTPS 하나만 연다 (문제 4)

- 손님이 들어오는 입구를 HTTPS 하나로 통일했다. 평문 HTTP로 오면 아무것도 넘기지 않고 301로 HTTPS로 돌려보낸다.
- TLS는 입구 nginx에서 풀고(TLS 1.2·1.3만), 안쪽은 내부망 평문으로 둔다. HSTS 헤더로 브라우저가 이후 HTTPS로만 접속하게 한다.
- backend·색깔별 web·DB에는 공개 포트를 두지 않는다. Docker가 연 포트는 UFW를 거치지 않으므로, 앱 포트는 127.0.0.1에만 열거나 DOCKER-USER 규칙으로 막아야 한다.
- 공개 입구(CloudFront) 앞에 AWS WAF를 붙여 XSS·SQL 인젝션·과도한 요청이 실제로 막히는 것을 확인했다(AWS 관리형 규칙 2개 + IP당 요청 횟수 제한).
- 운영이라면 도메인 + ACM 인증서(CloudFront나 ALB에서 TLS 종료) + 보안 그룹은 443만 연다.
