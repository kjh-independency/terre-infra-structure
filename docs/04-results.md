# 5. 업그레이드 결과

## 지도 타일: 0명에서 75명으로

**0명의 뜻:** 부하는 동시 사용자 10·25·50·75·100명 단계로 걸었다. 개선 전에는 가장 낮은 10명 단계부터 p95가 1.4초로 목표(1초)를 넘어, 통과한 단계가 하나도 없었다. 그래서 '목표를 지킨 최대 동시 사용자'가 0명이다. 동시 10명도 버티지 못했다는 뜻이다.

| 동시 사용자 | 개선 전 p95 | 개선 후 p95 |
| --- | --- | --- |
| 10명 | 1.4초 | 0.016초 |
| 25명 | 4.1초 | 0.030초 |
| 50명 | 11.4초 | 0.31초 |
| 75명 | — | 0.84초 |
| 100명 | 17.7초 | 1.40초 |

- 초당 처리량은 52~56건에서 멈춰 있다가 최대 738건으로 약 13배가 됐다. DB CPU는 상한(200%)에 붙어 있다가 최대 114%로 내려왔다. 에러는 0%.
- 경계 타일(보호지역·시군구·읍면동)은 100명에서도 p95 0.05~0.09초다. 100명에서 목표를 넘긴 것은 아직 backend가 처리하는 레이어 목록·지형 타일이다(다음 병목).
- 보호지역을 비공개로 바꾼 뒤 옛 주소에서 사라지기까지 3.9초가 걸렸다(허용 기준 5초 이내).

## 서버와 분리된 행정구역 지도

배포(backend·web 다시 만들기) 중에 같은 행정구역 타일을 0.5초마다 두 경로로 받았다.

| 경로 | 실패 | 끊긴 시간 |
| --- | --- | --- |
| 서버 nginx | 96건 / 602건 | 48.0초 |
| S3 + CloudFront | 0건 / 602건 | 0초 |

행정구역 지도는 이제 서버의 배포·장애와 상관없이 나간다. 사용자가 몰려도 엣지가 받아 서버는 늘어난 요청을 모른다.

## 배포: 무중단 + 자동화

| 지표 | 개선 전 | 블루-그린 1차 | 보완 후 |
| --- | --- | --- | --- |
| 실패한 요청 | 404건(13.6%) | 2건(0.07%) | **0건 / 4,200건** |
| 끊긴 시간 | 43.8초 | 0.7초 | **0초** |
| 1초 넘은 요청 | — | 1,046건 | 11건 |
| 새 버전 준비 시간 | — | 124.6초 | 94.8초 |

- '개선 전'은 3장 T3 진단 값이다. 같은 시험을 11/14에 다시 해도 15.4%·49초로 비슷하게 끊겼다(재현).
- push 한 번으로 검사 → 빌드 → 배포까지 3분 56초에 끝난다(배포 자체는 77초).
- 새 버전이 준비되지 않았던 실제 사례(7장)에서 파이프라인은 전환하지 않고 실패로 끝났고, 서비스는 그동안 옛 버전으로 계속 정상 응답했다.

## 백업·입구

- **백업:** 매일 05:10 자동 실행. DB 340MB → 덤프 109MB, 덤프 17초 + 업로드 1초(전체 31초). S3에서 크기·암호화·버전·만료일을 확인했다.
- **입구:** 평문 접속 → 301, HTTPS → 200(HTTP/2, TLS 1.3), HSTS 1년. 실험실의 모든 포트는 서버 안(127.0.0.1)에만 열려 있고 앱 컨테이너의 공개 포트는 0개다.
- **WAF:** 정상 요청 200, XSS 403, SQL 인젝션 403. 요청을 누적해 보내자 횟수 제한에 걸려 403. 차단은 CloudFront에서 일어나 원본에 닿지 않았다.

## 정직하게 적는 점

- 사업장 분석은 목표에 못 미쳤다. 타일 몫은 사라졌지만 위치마다 다른 분석 계산이 DB CPU를 여전히 다 쓴다. 다음 단계는 쿼리 개선과 DB 분리·증설이다.
- 지도 부하 시나리오는 줌 7~12만 요청해 모두 미리 만든 범위 안이다. 실제 줌 13~14는 backend가 처리한다.
- 수치는 CPU 2개로 묶인 실험실 값이다. 운영 성능 그 자체가 아니라 같은 조건의 전후 비교다.
- 보호지역 숨김의 개선 전 값(즉시)은 설계상 값이고 실측하지 않았다.
- HTTPS 입구는 실험실에서 구성·검증했다. 공용 서버의 운영 입구와 방화벽은 바꾸지 않았고, 인증서는 자체 서명이다.
