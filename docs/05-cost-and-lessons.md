# 6. 비용과 제약

## 비용

| 항목 | 쓴 것 | 비용 |
| --- | --- | --- |
| S3(행정구역 타일) | 파일 20,999개, 6.75MB | 월 1센트 미만 |
| CloudFront | 시험 요청 수만 건 수준 | 사실상 0(무료 사용량 안) |
| S3(백업) | 하루 109MB × 7일 보관 | 월 약 2센트 |
| AWS WAF | 규칙 3개를 약 6분 적용 | 약 1센트 |
| IAM·OIDC | 역할 1개, OIDC 공급자 | 무료 |
| GitHub Actions·GHCR | 비공개 저장소 무료 사용량 안 | 0 |

- 합계는 1달러 미만으로 예상한다(12/2 자원 정리 뒤 청구 화면으로 확정).
- 원칙: 서버를 새로 빌리지 않았다. AWS는 보관·전달·입구처럼 쓴 만큼만 내는 관리형 서비스에만 썼고, 보관 기간을 정해 비용 상한을 두었다. 시험용 자원은 시험이 끝나면 바로 지웠다.
- GitHub 계정에는 결제 수단이 없어, 무료 사용량을 넘으면 요금이 붙는 대신 실행이 멈춘다.

## 제약

- **공용 서버:** 팀 서비스가 돌고 있는 서버라 방화벽·바깥 포트·운영 서비스는 바꾸지 않았다. 개선은 모두 운영과 분리한 실험실(terre-lab)에서 했다.
- **운영 보호 장치:** 실험실 전체를 CPU 2개·메모리 4GB로 묶고 우선순위를 낮췄다. 시험 중 운영 응답을 10초마다 확인하고, 팀 CI가 시작되면 부하를 멈춘다. 배포·백업도 팀 CI가 돌면 기다리고, 새벽 백업 시간을 피한다. 공용 서버에 더한 것은 배포용 제한 SSH 키 한 줄뿐이고, 실험실 정리 때 뺀다.
- **수치의 범위:** 실험실은 CPU 2개라 운영(4개)보다 절대값이 크다. 같은 조건에서의 전후 비교로 읽어야 한다.
- **기간:** 서버는 11/27에 회수되어 실험은 11/26까지, 개인 AWS 자원은 12/2 전에 정리한다.
- **도메인 없음:** HTTPS는 자체 서명 인증서로 구성했다.
- **앱 코드는 그대로:** 인프라(Compose·nginx·스크립트·AWS)만 바꿨다. 쿼리 개선은 범위 밖이다.

## 하지 않은 것

| 항목 | 이유 |
| --- | --- |
| DB 분리·증설 | 계산을 없애는 쪽을 먼저 했고, 남은 사업장 분석 병목의 다음 단계로 둠 |
| RPO 1시간(WAL 보관) | 백업 위치 분리를 먼저 했다. 주기 단축은 설계로 남김 |
| S3 백업에서 복원 시험 | 서버 안 백업으로는 복원을 실측했다(67초). S3 사본 복원은 하지 않았다 |
| 서버 밖 감시·알림 | 이번 범위 밖 |
| 인프라 코드화(Terraform) | AWS 자원은 CLI 명령으로 만들고 기록해 다시 만들 수 있게 했다 |

# 7. 배운 점

## 배운 점

1. **병목은 추측하지 말고 잰다.** 지도가 느린 이유를 '타일이 무거워서'로 생각하기 쉽다. 그런데 전부 미리 만드는 데 103초밖에 안 걸렸다. 원인은 같은 계산의 동시 반복이었고, 그래서 해법도 DB 증설이 아니라 반복 제거가 됐다.
2. **옮기면 빠지는 것이 있다.** 타일을 S3로 옮기자, 서버 nginx에는 있던 '없으면 backend로' 대체 경로가 사라져 범위 밖 타일이 403이 됐다. 새 구성은 옛 구성이 암묵적으로 하던 일까지 확인해야 한다.
3. **한 서버의 블루-그린은 자원을 나눈다.** 무중단 배포를 넣자 실패는 거의 사라졌지만, 새 버전이 준비되는 동안 서비스가 느려졌다. 준비 중에만 CPU를 묶자 1초 넘은 요청이 1,046건에서 11건으로 줄고, 준비 시간도 오히려 짧아졌다.
4. **안전장치는 실제로 밟혀 봐야 믿을 수 있다.** 개인 저장소로 옮기며 기록을 지우다, 이미 DB에 적용된 마이그레이션 파일(V21)의 주석까지 고쳤다. Flyway 체크섬이 달라져 새 버전이 뜨지 못했고, 준비 확인에서 막혀 전환되지 않았다(서비스 영향 0). 로그로 원인을 찾아 원본으로 되돌린 뒤 재배포했다. 교훈: 적용된 마이그레이션은 한 글자도 바꾸지 않는다.
5. **문서보다 실제 기록을 본다.** GitHub OIDC로 AWS 역할을 받는 처음 시도가 거부됐다. GitHub가 보내는 신원이 예상한 이름 형식이 아니라 계정·저장소의 고유 번호가 붙은 형식이었다. CloudTrail의 실패 기록에서 실제 값을 확인해 맞췄다. 번호 형식은 같은 이름의 저장소를 만들어도 통과하지 못해 더 안전하다.
