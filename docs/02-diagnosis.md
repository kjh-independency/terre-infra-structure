## 문제 1. DB가 무거운 공간 계산을 요청마다 새로 한다

지도 경계 타일(보호지역·행정구역)은 요청이 올 때마다 DB(PostGIS)가 계산해서 만든다. 사업장 분석도 주변 보호지역·보호종을 매번 공간 연산으로 구한다. 이 계산이 DB CPU를 모두 차지해서, 동시 사용자 10~25명에서 이미 목표를 넘긴다.

| 동시 사용자 | 지도 타일 p95 | 사업장 분석 p95 |
| --- | --- | --- |
| 10명 | 1.4초 | 0.22~0.27초 |
| 25명 | 4.1초 | 1.39초 |
| 50명 | 11.4초 | 4.9~5.1초 |
| 100명 | 17.7초 | 11.3~12.3초 |

- **처리량 천장:** 사용자를 늘려도 초당 처리량은 지도 타일 52~56건(10명부터), 사업장 분석 44~52건(25명부터)에서 더 늘지 않았다. 늘어난 사용자는 대기 줄만 길게 만든다.
- **DB CPU:** 두 시험 모두 실험실 DB CPU가 191~200%로 상한(200%)에 계속 붙어 있었다.
- **대조군:** 미리 만들어 둔 파일에서 읽는 지형(dem) 타일은 같은 조건 10명에서 68ms였다. 같은 서버라도 DB 계산을 거치지 않으면 빠르다.
- **연결 풀은 원인이 아니라 결과:** 사업장 분석에서 25명부터 backend의 DB 연결 10개가 모두 사용 중인 순간이 절반 가까이 됐다. 하지만 DB CPU가 이미 한계라, 쿼리가 CPU를 기다리느라 연결을 오래 붙잡은 결과다. 연결 수를 늘리는 것은 해법이 아니다.
- **재현:** 사업장 분석은 11/12·11/13 두 번 측정해 같은 결과를 얻었다. 지도 타일은 11/5 팀 측정(CPU 4개, 50명 p95 5.5초)과 비교해 CPU가 절반일 때 약 2배 느려, 같은 원인임을 확인했다.
- **범위 밖:** 사업장 분석 중 region 요청은 10명에서도 p95 6~7초로 쿼리 자체가 무겁다. 앱 코드 영역이라 인프라 개선 범위에서 빼고 기록만 한다.

## 문제 2. backend가 하나뿐이라 배포와 장애 때마다 서비스가 끊긴다

backend(Spring Boot)는 1개만 떠 있고, 새로 시작해 요청을 받을 준비가 되기까지 37~44초가 걸린다. 그동안 요청을 대신 받을 곳이 없다.

| 상황 (1초에 10번 요청하며 5분 관찰) | 실패한 요청 | 끊긴 시간 |
| --- | --- | --- |
| 배포 (develop 머지 때 자동 배포와 같은 방식) | 404건 / 2,969건 (13.6%) | 43.8초 |
| backend 강제 종료 | 354건 / 3,001건 (11.8%) | 36.8초 |
| DB 강제 종료 (비교) | 1건 / 3,001건 (0.03%) | 없음 (약 2초 지연) |

- **교체 방식:** 배포는 docker compose가 backend·screening·web을 먼저 모두 내리고 다시 올린다. web(입구)은 backend가 준비된 뒤에야 시작해서, 처음 1초는 502, 이어 43초는 접속 자체가 안 됐다.
- **원인:** 끊긴 시간(36.8~43.8초)이 backend 시작 시간(복원 시험에서 39초)과 거의 같다. "기존 것을 먼저 내리고 새 것이 준비될 때까지 기다리는" 교체 방식과 backend 1개 구성이 원인이다.
- **빈도:** develop에 머지될 때마다 운영 서버에 자동 배포되므로, 머지마다 이 끊김이 생긴다.
- **DB는 약점이 아님:** DB는 강제 종료돼도 몇 초 만에 자동 재시작됐고, 그사이 backend 연결 풀이 기다려 줘서 실패가 1건뿐이었다.

## 문제 3. 백업이 서버와 운명을 같이하고, 최대 24시간치를 잃는다

매일 04:00 DB를 통째로 백업(gzip, 약 110MB)해 같은 서버 디스크에 7일 보관한다.

| 항목 | 값 |
| --- | --- |
| 복원 시간(RTO) | 67초 (DB 복원 15초 + 통계 갱신 13초 + 앱 시작 39초) |
| 복원 검증 | 오류 0, 보호종 62,604건·보호지역 19,986건·스키마 버전 일치 |
| 잃을 수 있는 데이터(RPO) | 최대 24시간 (하루 1번 백업) |
| 백업 위치 | 운영 서버와 같은 디스크, 서버 밖 사본 없음 |
| 백업에 없는 것 | 업로드 파일, Redis, 설정 파일 |

- **복원 속도는 충분:** 67초로 목표(30분)보다 훨씬 빠르다. 하지만 이 값은 서버와 디스크가 살아 있을 때만 성립한다.
- **같이 사라지는 백업:** 디스크 고장, 서버 삭제, 실수로 지우기 같은 사고에서는 원본과 백업이 함께 사라져 복구 자체가 불가능하다. 실제로 이 서버는 11/27에 회수될 예정이다.
- **데이터 손실:** 하루 1번 백업이라, 백업 직전에 사고가 나면 최대 24시간치 데이터를 잃는다(목표 1시간).
- **개선 초점:** 복원 속도가 아니라 백업 위치(서버와 분리)와 백업 주기다.

## 문제 4. 앱 포트가 밖에 직접 열려 있고 HTTPS가 없다

11/6 점검 결과다.

- 밖에서 열린 포트는 22(SSH)와 8088(web)이다. web이 모든 주소에 8088로 열려 있어 앱 포트가 바로 노출된다.
- HTTPS가 없어 로그인 쿠키가 Secure 설정 없이 평문 HTTP로 오간다(COOKIE_SECURE=false).
- Docker가 연 포트는 서버 방화벽(UFW)을 우회하고 클라우드 방화벽은 1024~65535를 열어 두어, 컨테이너 포트를 실수로 열면 그대로 밖에 노출된다.
- 11/14 재점검(읽기만): 밖에서 받는 포트는 22·80·8088이다. 운영 web은 Docker가 0.0.0.0:8088로 직접 공개하고, Docker 공개 포트를 걸러 주는 DOCKER-USER 체인이 비어 있다. 그래서 UFW에서 8088을 막아도 실제로는 열려 있는 구조다. UFW는 443을 허용하지만 443을 받는 프로그램은 없다(HTTPS 입구 없음). DB·Redis는 127.0.0.1에만 열려 있다(양호).

## 관찰. 빌드와 서비스가 같은 서버에서 돈다

GitLab Runner가 운영 서버 안에 있어서, 머지 전 MR 테스트와 배포 빌드가 모두 운영 서버 CPU를 쓴다. 11/12 밤 팀 MR 파이프라인(작업 2개 동시, CPU 3개 이상)이 도는 동안 운영 응답이 평소 0.07초에서 0.11~0.21초(최대 0.37초)로 느려졌다. 의도한 시험이 아니라 우연히 1번 관찰한 것이라 근거로는 약하지만, 빌드와 서비스를 분리해야 하는 이유를 보여 준다. 서버가 GitLab 이미지 저장소에 접속할 수 없어 운영 서버에서 직접 빌드하는 구조다.

## 정리: 개선할 축

| 축 | 문제 | 4장에서 비교할 방향 |
| --- | --- | --- |
| 타일·분석 | DB가 같은 계산을 요청마다 반복 | 일 줄이기(캐시, 미리 생성) vs 힘 키우기(DB 분리·증설) |
| 배포·가용성 | backend 1개, 끄고 켜는 교체 | 무중단 배포(새 것을 먼저 띄우고 전환) |
| 백업·복구 | 같은 디스크, 하루 1번 | 서버 밖 사본, 백업 주기 단축 |
| 입구 | 앱 포트 노출, HTTPS 없음 | 입구 하나, 앱 포트는 내부 전용 |
| 빌드 | 운영 서버에서 빌드 | 빌드 분리 |

## 측정의 한계

- 실험실은 CPU 2개로 묶여 있어 운영(4개)보다 절대값이 크게 나온다. 이 값은 운영 성능 그 자체가 아니라, 같은 조건에서 전후를 비교하기 위한 기준값이다.
- 각 단계는 2분씩 측정했다. 사업장 분석은 2번 측정해 재현을 확인했고, 나머지는 1번 측정했다.
- 시험 대상은 11/6 구성이다. 그 뒤 팀이 넣은 변경(타일 서버 캐시 등)은 포함하지 않았다.
